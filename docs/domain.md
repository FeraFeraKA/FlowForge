# Domain contracts

These contracts are used by the deployed Go API and React frontend.
[Deployment](deployment.md) describes hosting and environment configuration;
[HTTP](http-api.md) defines the public DTO boundary. All repositories currently
live in memory, so restart clears definitions and runs.

## Identifiers and time

- Pipeline and Run IDs are generated by the backend and are opaque strings.
- Job IDs are supplied by the client and are unique within one pipeline.
- IDs must be non-empty and contain only ASCII letters, digits, `_`, and `-`.
- Timestamps are UTC RFC 3339 strings.
- Duration configuration uses Go duration strings such as `"500ms"`, `"2s"`, or
  `"1m30s"`. A missing optional duration is represented by omission, not by an
  empty string.
- Jobs are represented as arrays in JSON. Their order is preserved for stable UI
  display but has no scheduling meaning.

Generated pipeline IDs currently use `pl_` and run IDs use `run_`, followed by
32 hexadecimal characters from 16 random bytes. Clients must still treat them
as opaque and must not depend on that implementation detail.

## Pipeline

```json
{
  "id": "pl_opaque",
  "name": "Build and deploy",
  "maxParallel": 2,
  "jobs": [],
  "createdAt": "2026-08-01T12:00:00Z"
}
```

Invariants:

- `name` is non-empty after trimming;
- `maxParallel` is at least 1;
- the pipeline contains at least one job;
- job IDs are unique;
- every dependency refers to another job in the same pipeline;
- a job cannot depend on itself;
- the dependency graph is acyclic.

## JobDefinition

The MVP public executor type is `delay`.

```json
{
  "id": "tests",
  "name": "Run tests",
  "type": "delay",
  "dependsOn": ["install"],
  "timeout": "5s",
  "maxRetries": 2,
  "retryDelay": "500ms",
  "config": {
    "duration": "2s"
  }
}
```

Rules:

- `name` and `type` are required;
- `dependsOn` contains no duplicates;
- `maxRetries` is the number of extra attempts, so `2` permits three attempts;
- `maxRetries` is non-negative;
- `retryDelay` is non-negative and only matters when retries are enabled;
- `timeout`, when present, is positive and applies to each attempt separately;
- timeout is a retryable attempt failure while attempts remain;
- `config.duration` for `delay` is required and positive;
- unknown executor types or unknown config fields fail validation.

The deployed code has only the deterministic `DelayExecutor`. Scheduler
failure/retry tests use a deterministic fake executor rather than randomness.

## Run

```json
{
  "id": "run_opaque",
  "pipelineId": "pl_opaque",
  "pipelineName": "Build and deploy",
  "status": "running",
  "maxParallel": 2,
  "jobs": [],
  "createdAt": "2026-08-01T12:01:00Z",
  "startedAt": "2026-08-01T12:01:00Z",
  "finishedAt": null
}
```

A run stores the effective job definitions needed to understand and retry it. It
does not read a mutable pipeline during execution.

Run statuses:

- `pending`: created but not yet accepted by the scheduler;
- `running`: the coordinator is scheduling or waiting for work;
- `completed`: all jobs completed successfully;
- `failed`: at least one job finally failed; downstream jobs may be blocked;
- `cancelled`: cancellation won before a terminal result was committed.

Allowed transitions:

```text
pending -> running
pending -> cancelled
running -> completed
running -> failed
running -> cancelled
```

Terminal states cannot transition. Cancelling a terminal run is a conflict.

## JobRun

```json
{
  "jobId": "tests",
  "name": "Run tests",
  "status": "running",
  "attempt": 1,
  "progress": 0,
  "error": null,
  "startedAt": "2026-08-01T12:01:02Z",
  "finishedAt": null
}
```

`attempt` starts at `0` before the first execution and becomes `1` when the first
attempt starts. `progress` is an integer from 0 through 100. Delay jobs need not
emit continuous progress; the current executor reaches 100 on success.
This state example omits the effective definition fields for brevity; REST
JobRun DTOs also include type, dependencies, timeout, retries, and delay config.
There is no public `logs` field or shell stdout/stderr history.

Allowed transitions:

```text
pending  -> queued | blocked | cancelled
queued   -> running | cancelled
running  -> completed | failed | cancelled
failed   -> retrying
retrying -> queued | cancelled
```

`failed` is temporarily non-terminal only when another retry has already been
decided. If no retry remains, it is terminal. This distinction must be represented
by scheduler logic rather than arbitrary external status writes.

Dependency rules:

- a job becomes ready only when every dependency is `completed`;
- a dependency in `failed` with a scheduled retry does not block downstream jobs;
- after a dependency finally fails, all jobs that can no longer run become
  `blocked`;
- blocked jobs are never sent to an executor;
- a run with any final failed job finishes as `failed` after all running work has
  settled and all impossible downstream work is blocked.

Cancellation rules:

- pending, queued, retrying, and currently running jobs that have not already
  committed a terminal result become `cancelled`;
- completed, finally failed, and blocked jobs keep their terminal history;
- if cancellation is processed before the run commits another terminal state,
  the run finishes as `cancelled`.

## Retry of a failed or cancelled Run

`POST /api/runs/{runID}/retry` creates a new run from the original run's stored
definition snapshot. It never reopens or mutates the old run. The response exposes
the new run ID.

Only failed or cancelled runs may be retried. A successfully completed or still
active run returns a conflict. To execute a successful pipeline again, start a new
run through `POST /api/pipelines/{pipelineID}/runs`.
